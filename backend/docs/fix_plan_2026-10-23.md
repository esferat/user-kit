## B-01. Заблокированный аккаунт должен терять доступ

**Где:** `application/account/CurrentAccountService.java:37-45` (метод `resolve`).

**Проблема:** `enabled` сохраняется (`AccountAdminUseCases.java:41-42`) и отдаётся в DTO
(`AccountDto.java:35`), но `resolve()` создаёт `CallerContext` без проверки. `CallerContext`
(`application/account/CallerContext.java:9`) вообще не содержит `enabled`.

**Что сделать:**
1. После загрузки/создания аккаунта в `resolve()`:
   ```java
   Account account = ...;
   if (!account.isEnabled()) {
       throw DomainException.forbidden("The account is disabled");
   }
   return new CallerContext(account.id(), account.email(), account.isAdmin());
   ```
   `DomainException.forbidden` уже даёт 403 и код `forbidden` (`domain/shared/DomainException.java:57-59`).
2. Решить, что делать с уже выданными сессиями: минимум — проверка на каждом запросе (пункт 1).
   Опционально добавить в `SessionRepository` метод `deleteBySubject(String subject)` и вызывать
   его из `AccountAdminUseCases.update`, когда `enabled` стал `false`. Для этого нужен новый
   запрос в `AuthSessionRowRepository` (`delete ... where subject = :subject`).
3. Контроллеры, которые не вызывают `resolve()` (см. `B-02`), тоже должны начать его вызывать —
   иначе блокировка не сработает для админских ручек.

**Критерии приёмки:**
- С валидной cookie заблокированного пользователя `GET /api/v1/me`, `GET /api/v1/files`,
  `GET /api/v1/users` возвращают 403, а не 200.
- Разблокировка возвращает доступ без перелогина (если сессии не удалялись) в рамках TTL.
- Добавлен unit-тест `CurrentAccountServiceTest`: `enabled=false` → `DomainException` c `kind=FORBIDDEN`.

**Проверка:** команда backend-тестов (см. низ файла) + новая проверка в `scripts/smoke.ps1`.

## B-02. Авторизация админских API по локальной роли

**Где:** `config/SecurityConfig.java:86-87` (`hasRole("ADMIN")`),
`adapters/in/security/OidcJwtAuthenticationConverter.java:25-28` (роли из claims),
`adapters/in/web/account/UserAdminController.java:37-56` (нет `CurrentAccountService`).

**Проблема:** `admin`, снятый через `PATCH /api/v1/users/{id}` (`AccountAdminUseCases.update`),
остаётся в JWT/ID-token. Security-цепочка доверяет claim'ам, поэтому админские ручки продолжают
работать. Refresh у IdP возвращает ту же роль.

**Что сделать (выбрать один вариант и записать решение в этом файле):**

- **Вариант A, минимальный:** в `UserAdminController` внедрить `CallerResolver` (уже есть) и
  `CurrentAccountService`; в каждом методе получить `CallerContext` и проверить `caller.admin()`,
  иначе `DomainException.forbidden(...)`. В `SecurityConfig` заменить `hasRole("ADMIN")` на
  `authenticated()` для `/api/v1/users/**`; `/api/v1/admin/**` — так же, если появится.
- **Вариант B, рекомендуемый:** объявить `AuthorizationManager<RequestAuthorizationContext>`,
  который резолвит аккаунт через `CallerResolver` + `CurrentAccountService` и проверяет
  `admin && enabled`. Подключить его в `authorizeHttpRequests`. Убрать `hasRole` из правил
  приложения, оставив IdP только аутентификацией.

**Важно:** не делать `resolve()` внутри `OidcJwtAuthenticationConverter` «на каждый запрос» без
кэша на request — это удвоит обращения к БД. Если нужен именно конвертер, кэшируй результат в
`request.setAttribute(...)` и переиспользуй в контроллерах.

**Критерии приёмки:**
- `PATCH /api/v1/users/{id}` с `roles:["user"]` для самого себя → следующий `GET /api/v1/users`
  с той же cookie отдаёт 403 (без перелогина и без ожидания истечения токена).
- Пользователь с claim `admin`, но локально `user`, не получает доступ к `/api/v1/users`.
- Пользователь с локальным `admin`, но без claim (если такое допускается продуктом) — решить
  явно; по умолчанию доступ не давать.
- Интеграционный тест MockMvc на оба сценария.

## B-03. SQL-пагинация, фильтры и сортировка

**Где:**
- `application/file/FileUseCases.java:42-46`, `adapters/in/web/file/FileController.java:73-78`;
- `domain/file/FileRepository.java:16-19`, `adapters/out/persistence/file/JpaFileRepository.java:34-41`;
- `application/account/AccountAdminUseCases.java:23-26`, `adapters/in/web/account/UserAdminController.java:52-56`;
- `adapters/out/persistence/account/JpaAccountRepository.java:35-36`, `UserAccountRow.java:40-43`.

**Проблема:** репозитории возвращают все строки, контроллеры фильтруют/сортируют/режут в памяти.
`page/size` не доходят до SQL. `roles` — `EAGER`-коллекция, отсюда N+1 на список пользователей.

**Что сделать:**
1. В `domain/shared` добавить `PageQuery(int page, int size)` (без Spring) и использовать
   `PageResult<T>` как результат.
2. В портах объявить методы с `PageQuery` и критериями:
   - `FileRepository.searchVisible(String search, UUID ownerId, String sort, PageQuery query)`;
   - `AccountRepository.search(String search, String sort, PageQuery query)`.
3. В JPA-адаптерах: `Pageable` (`PageRequest.of(page, size, sort)`), `countQuery` для JPQL,
   `lower(...) like :term`, join fetch владельца (`FileObjectRow`) и
   `@EntityGraph(attributePaths = "roles")` (или `@BatchSize`) для аккаунтов.
4. Сортировку валидировать по белому списку (`name`, `createdAt`, `sizeBytes`, `email`,
   `updatedAt` + направление); неизвестное — 400 `invalid_sort`, не 500.
5. Контроллеры только собирают параметры и отдают `PageResult`; `FileUseCases.listVisibleTo`
   и `AccountAdminUseCases.findAll()` удалить или переписать на страницы.
6. `PageResult.of(...)` оставить для уже готовых списков (см. `B-10`), для БД использовать
   перегрузку `PageResult.of(Page<?>)`.

**Критерии приёмки:**
- При 120 файлах `GET /api/v1/files?page=2&size=50` отдаёт 20 элементов и `total=120`.
- Поиск и сортировка работают на уровне SQL; в логах Hibernate нет `select` всей таблицы.
- Число SQL-запросов на страницу пользователей не растёт с `size` (N+1 устранён).
- Тест репозитория на 3 аккаунта/страницу 2 + тест контроллера на валидацию `sort`.

## B-04. Убрать HTTP-вызовы из транзакций

**Где:** `application/auth/AuthenticationUseCases.java:110-127` (`completeLogin`),
`:167-182` (`closeSession`), `:185-194` (`refresh`).

**Проблема:** `@Transactional` держит соединение и блокировки на время запроса к IdP. Пул — 10
соединений (`application.yml`), поэтому таймаут IdP останавливает API.

**Что сделать:**
1. Разбить каждый сценарий на короткие транзакции через `TransactionTemplate` (внедрить в
   `AuthenticationUseCases`):
   - `completeLogin`: tx1 — найти и удалить `LoginState`; вне tx — `exchangeCode` и `subjectOf`;
     tx2 — `sessions.deleteOlderThan(...)` + `sessions.save(...)`.
   - `refresh`: tx1 — прочитать сессию; вне tx — `provider.refresh(...)`; tx2 — обновить сессию.
   - `closeSession`: tx1 — прочитать; tx2 — удалить; revoke — после коммита.
2. Не выносить эти методы в приватные `@Transactional` внутри того же бина — Spring-прокси не
   сработает (self-invocation). Либо `TransactionTemplate`, либо отдельный бин-помощник.
3. Сохранить текущее поведение: `LoginState` удаляется до обмена кода (защита от replay).

**Критерии приёмки:**
- В тесте fake-`IdentityProvider` проверяет
  `TransactionSynchronizationManager.isActualTransactionActive() == false` во время вызова.
- Ошибка IdP не оставляет «висящих» транзакций и не удаляет валидную сессию (см. `B-05`).

## B-05. Гонка refresh не должна разлогинивать

**Где:** `adapters/in/security/SessionTokenFilter.java:87-101`,
`application/auth/AuthenticationUseCases.java:185-194`; удаление сессии —
`SessionTokenFilter.java:80-81`.

**Проблема:** параллельные запросы берут один rotating refresh token. Keycloak принимает один,
второй получает `invalid_grant`, после чего cookie очищаются — пользователь вылетает.

**Что сделать:**
1. Сериализовать refresh по сессии. Для одного инстанса достаточно striped-lock:
   ```java
   private final ConcurrentHashMap<String, ReentrantLock> locks = new ConcurrentHashMap<>();
   ```
   Внутри лока **перечитать** сессию из БД, затем вызвать `refresh` (вне DB-транзакции, см. `B-04`).
2. Перед удалением сессии при ошибке refresh сравнить актуальный `refreshToken` в БД с тем,
   который использовался. Если он уже заменён другим запросом — сессию не удалять, повторить
   refresh с новым токеном.
3. Для нескольких инстансов заменить лок на БД-advisory-lock или внешний lock; зафиксировать
   ограничение в комментарии.
4. Не очищать cookie при временной ошибке IdP (5xx/таймаут): это не признак мёртвой сессии.

**Критерии приёмки:**
- Два параллельных запроса с истёкшим access token не приводят к 401/очистке cookie.
- Тест: два потока вызывают `accessToken(...)` с mock-провайдером, который ротирует refresh;
  оба получают рабочий токен, сессия жива.

## B-06. Конкурентное изменение → 409, а не 500

**Где:** `adapters/out/persistence/account/JpaAccountRepository.java:47-52`,
`adapters/out/persistence/file/JpaFileRepository.java:54-59`,
`adapters/in/web/ApiExceptionHandler.java:103-110`.

**Что сделать:**
1. Добавить в `ApiExceptionHandler` обработчик **до** общего `Exception`:
   ```java
   @ExceptionHandler(ObjectOptimisticLockingFailureException.class)
   ResponseEntity<ApiError> handleConflict(...) // 409, code="conflict"
   ```
   Проверить, что Spring оборачивает `OptimisticLockException` именно в этот тип.
2. Ручную проверку версии оставить для случая с `If-Match`, но при гонке без заголовка отдавать
   409 с актуальным ETag в теле (поле `etag`) или в заголовке — как в `docs/api.md`.
3. Добавить тест: два параллельных `PATCH` без `If-Match` → один 200, второй 409 (не 500).

**Критерии приёмки:** контракт `{timestamp,status,code,message,path,violations}` соблюдён,
`code=conflict`, статус 409.
