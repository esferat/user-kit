## [CRITICAL_RULES]

1. **Источники истины (в порядке приоритета):** код бэкенда, `docs/auth.md`, конфигурация Keycloak,
   `docker-compose.yml`/nginx, код `frontend-antd` как референс поведения фронтенда. Память и общие
   знания об OIDC — только для терминологии, но не как источник конкретных деталей проекта.
2. **Никаких выдуманных эндпоинтов, полей, кодов ошибок.** Всё, что попадает в документ, должно
   существовать в коде/конфиге. Если чего-то нет — это «Открытый вопрос», а не допущение в тексте.
3. Каждое функциональное требование получает **ID** (`FR-AUTH-001`, …) и ссылку на источник.
4. Каждый сценарий — в формате **Given / When / Then** либо нумерованными шагами с ожидаемым
   результатом.
5. Явно разделяй: **в scope** фичи Authorization и **вне scope** (регистрация — отдельная фича;
   изменение бэкенда/Keycloak — вне scope).
6. Описывай **наблюдаемое поведение**, а не реализацию: не «использовать cookie X в коде», а
   «сессия хранится в httpOnly cookie, недоступной JS».
7. Все ограничения безопасности фиксируй как **требования** (проверяемые), а не как пожелания:
   «токены не хранятся в localStorage/sessionStorage/DOM», «все не-GET запросы защищены CSRF-токеном».
8. Роли ровно две: `admin`, `user`. Опиши матрицу доступа. Роли — серверный контроль; скрытие UI —
   только UX.
9. Не дублируй в документе очевидное; приоритет — фактическое поведение этого проекта (домены,
   BFF-схема, двойные флаги и т.п.).
10. Термины — единообразно, с глоссарием. Язык — русский.
11. Если требование ненадёжно выводится из кода (например, поведение refresh-токена) — пометь как
    «требует подтверждения» и вынеси в открытые вопросы.
12. Документ должен быть пригоден для передачи разработчику и тестировщику как основа для реализации
    и тест-плана.

### Ключевые факты (проверить по источникам, не копировать слепо)

- Режимы: `mode ∈ {oidc, dev, none}`; поля конфига: `devEnabled`, `oidcConfigured`,

- Эндпоинты авторизации: `GET /api/v1/auth/config`, `GET /api/v1/auth/login`, `GET /api/v1/auth/callback`,

## [OUTPUT_FORMAT]

1. **План** — какие файлы создаёшь и в каком порядке, что берёшь из каких источников.
2. **Файлы документации** — для каждого: путь, назначение, ключевые разделы/таблицы (можно
   фрагментами в Markdown).
3. **Трассируемость** — таблица «требование → источник» (или ссылка на неё в документе).
4. **Открытые вопросы / допущения** — отдельным блоком.
5. **Ссылки на источники** — использованные файлы репо.

Правила оформления документации:

- Markdown; заголовки по уровням; таблицы для матриц и контрактов.
- Диаграммы — только Mermaid (код-блок).
- ID не переиспользовать и не менять при правках.
- Формулировки требований: «Система должна …».
- Никаких `TODO` без явного открытого вопроса.
- Язык — русский.


Запрещено: выдуманные эндпоинты/поля; требования без источника; отсутствие ID; английский язык;
выводы без указания источника.
