## N-01. Синхронизировать форматы аватара с backend

**Где:** `src/features/profile-edit/ui/ProfileEditForm.tsx:80` (`accept` включает
`image/webp,image/gif`), `:110` (текст «PNG или JPEG»);
backend: `backend/src/main/java/com/acme/usermark/application/profile/AvatarImages.java:33-40`
(декодирует только то, что понимает `ImageIO`; WebP стандартно не поддерживается).

**Проблема:** пользователь выбирает WebP, файл уходит на сервер и отклоняется `invalid_image`
уже после загрузки.

**Что сделать (выбрать вариант):**
- **A, минимальный:** `accept="image/png,image/jpeg"` и проверка в `beforeUpload`:
  ```ts
  if (file.type !== 'image/png' && file.type !== 'image/jpeg') {
    void message.error('Поддерживаются только PNG и JPEG.');
    return false;
  }
  ```
  Текст подсказки оставить «PNG или JPEG до 5 МБ».
- **B, если GIF нужен:** оставить `image/gif`, но проверить реальный рендер на backend
  (ImageIO читает GIF, результат — PNG) и обновить текст.
- **WebP:** либо убрать из UI, либо добавить поддержку на backend (например, TwelveMonkeys
  ImageIO plugin) отдельной задачей; без этого не рекламировать.

**Критерии приёмки:**
- WebP отклоняется на клиенте с понятным сообщением (вариант A).
- PNG/JPEG (и GIF, если оставлен) проходят и дают две версии.
- Текст и `accept` совпадают.

## N-02. Постоянные тесты для игровой логики

**Где:** `package.json:6-11` — нет test-скрипта; в репозитории нет `*.test.*`/`*.spec.*`.
Тестировать: `features/lines/game/engine.ts`, `features/match3/game/rules.ts`,
`features/lines/game/settingsStorage.ts`, `statsStorage.ts`.

**Что сделать:**
1. Добавить devDependencies: `vitest` (при необходимости `@vitest/coverage-v8`).
   В корне pnpm-workspace — установка через `pnpm add -D vitest --filter frontend-main`.
2. `package.json`:
   ```json
   "test": "vitest run",
   "test:watch": "vitest"
   ```
3. `vitest.config.ts`: `environment: 'node'`, alias `@` → `./src`.
4. Тесты (минимум):
   - `findPath`: прямой путь, обход препятствия, отсутствие пути, `from === to`.
   - `applyMove`: списание линии, бонусный ход, спавн на занятую клетку, `status='over'`.
   - `findHint`: возвращает ход со списанием при наличии; `null` для оконченной партии.
   - `createGame` с фиксированным seed детерминирован.
   - `match3/rules.findRuns`: горизонталь/вертикаль/пересечение/длина < 3.
   - `planSpecials`: 4 → молния, 5 → радужный, пересечение → бомба.
   - `expandClears`: цепная активация бомбы/молнии, `protectedKeys` не очищаются.
   - `settingsStorage/statsStorage`: мусор в `localStorage` → дефолт/пустой список;
     `recordAttempt` держит 5 лучших и сортирует.
     Для `window` в node-окружении использовать `vi.stubGlobal('window', { localStorage })`
     с простой реализацией или `environment: 'jsdom'` для этих файлов.
5. Добавить `pnpm test` в Definition of Done и, если есть CI, в пайплайн.

**Критерии приёмки:** `pnpm test` зелёный; тесты падают при намеренном изменении правил
(проверить хотя бы один).

## N-05. Частичное сохранение профиля

**Где:** `src/features/profile-edit/ui/ProfileEditForm.tsx:52-67` — сначала аватар, затем
`PATCH /api/v1/me`.

**Проблема:** если PATCH падает, аватар уже изменён, а форма показывает старые поля.

**Что сделать:**
1. Отслеживать `avatarSaved`/`avatarRemoved`.
2. В `catch`:
   - если аватар уже сохранён — `await auth.refresh()` (или `onSaved()` без редиректа), чтобы
     UI показал фактическое состояние;
   - сообщение разделить: «Аватар сохранён, данные профиля — нет» / общая ошибка.
3. Рассмотреть объединённый endpoint на backend (multipart с полями) как отдельную задачу,
   если частичные состояния недопустимы продуктом.

**Критерии приёмки:** после сбоя PATCH аватар в шапке и на экране соответствует серверу;
пользователь понимает, что сохранилось.

## N-06. Возврат на исходную страницу после входа

**Где:** `src/features/auth/api/cookieAuthProvider.ts:82-94` — всегда
`window.location.assign('/api/v1/auth/login')`; `LoginScreen.tsx:97` — `auth.login()` без
аргументов. Backend принимает только hash-возврат (`AuthenticationUseCases.appUri`), для
path-роутинга Next это не подходит.

**Что сделать (без изменения backend):**
1. Перед редиректом сохранять намерение:
   ```ts
   sessionStorage.setItem('auth:returnTo', window.location.pathname + window.location.search);
   ```
2. В `LoginScreen` после `auth.status === 'authenticated'`:
   ```ts
   const target = sessionStorage.getItem('auth:returnTo') ?? '/';
   sessionStorage.removeItem('auth:returnTo');
   router.replace(target);
   ```
3. Не сохранять `/login` и внешние URL; допускать только path, начинающийся с `/`.
4. Для dev-входа тот же механизм (страница не покидается).

**Критерии приёмки:** прямой заход на `/games/lines` без сессии → вход → возврат на
`/games/lines`; после обычного входа с `/` — остаётся `/`.
